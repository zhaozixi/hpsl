## 2. 范围与边界

### 2.1 In-Scope 已交付
1. **挑错触发四规则（F7.1）**：`TriggerRule` + `evaluate_triggers` + `should_trigger_critic`；规则 ③ 答案机分歧在 v0 恒 false（参数预留，v1 启用）。
2. **同源降级与异构判定（F7.2 / BD-03）**：`same_source` 复用 M4 `heterogeneous`；`record_same_source_warning` 写 `claim_check` 同源警告（agree=NULL，providers 含 same_source/keypoint 标记）；`evaluate_close` 接入 `is_keypoint`/`same_source`/`explicit_confirm` 决策，同源关键卡点拒绝自动闭环；`close_unit` 经显式确认闭环并标记「同源显式确认」留痕。
3. **用户仲裁**：`arbitrate` 支持 采纳/驳回/待验证；「待验证」不阻断闭环（仅入质量度量）。
4. **claim_check 落账（零 DDL）**：`write_claim_check` / `trigger_critic_if_needed` 经 `db.write` 同事务审计。
5. **A050001 守卫**：`rubric_reveal_allowed` / `filter_judgment_data` 保证评分要点仅在「产出+自评」后进入判定屏数据。
6. **治理计数（AC-5.4）**：`count_same_source_keypoint_auto_close` 同源关键卡点自动闭环违规次数恒为 0。
7. **测试**：`tests/test_claim_check.py`（23 例）。

### 2.2 Out-of-Scope（留待后续，未做）
- F7 界面编排（并排分歧视图 / 同源警告条 / 判定一屏按钮）属 M10；v1 多答案机分歧（规则 ③）、评分要点第二厂商核对（O6）属 v1（M6+）；真实 LLM 挑错调用由 M10 接线；HTTP 路由暴露属 M10。

## 3. 与锁定基线的偏差与实现决策（须记录）

| # | 偏差/决策 | 原因 | 处理 | 影响 |
|---|-----------|------|------|------|
| D-M5-1 | 补注册 `A050001` 于 `common/errors.py` | 基线 §3.5.1 标注 M5 须注册 A050001（评分要点作答前不可见），但 `errors.py` 此前仅含 A050002/3/4 等，未注册 A050001；不注册则 `BizError` 抛 `KeyError` | 在 `errors.py` 新增 A050001（仅数据登记，不改既有逻辑语义） | 符合「仅 errors.py 可改」纪律；错误码空间无冲突 |
| D-M5-2 | `has_unresolved_keypoint` 残留门控精确化为「阻断性残留」 | M4 用 `residual=1`（任意）判定阻断；M5 须对齐 §5.5「待验证不阻断、驳回不阻断」 | WHERE 增加 `AND (user_ruling IS NULL OR user_ruling='采纳')`；M4 既有测试（residual=1 且 NULL 裁决）仍命中阻断，向后兼容 | 新增「待验证/驳回」不阻断语义，更贴合基线；零 DDL |
| D-M5-3 | 引擎读取 `claim_check.providers` 增加 `_providers_of` 解码 | `db.query` 按设计**不自动解析 JSON 列**（docstring 明示「调用方按需处理」），`providers` 以 JSON 文本返回 | `claim_check.py` 新增 `_providers_of(row)`（str→dict 安全解码），用于 `mark_same_source_confirmed` / `count_same_source_keypoint_auto_close` | 不改动 db.py；调用方负责解码，符合既有约定 |
| D-M5-4 | BD-03 同源关键卡点拒绝自动闭环复用 `A020001`（带 BD-03 专属 `block_reason` 文案），不新增错误码 | M5 错误码空间仅分配 A050001–A050004，BD-03 为「UX 门控」而非独立业务错误；新增码会越出基线错误码表 | `CloseDecisionVO` 增加 `ss_keypoint_block` / `block_reason`；`close_unit` 在 `close_allowed=False` 时以 `block_reason` 文案抛 `A020001` | 文案明确区分「未达标」与「同源关键卡点需显式确认」；不污染错误码表 |
| D-M5-5 | 关键卡点标记与同源判定以**运行时参数**传入（`is_keypoint` + 两模型 ID），而非落库字段 | `unit` 表为 M0 冻结 16 库对象之一，无 `is_keypoint` 列；同源判定须基于模型配置（registry）在闭环时实时计算 | 闭环门控经 `evaluate_close(is_keypoint=, same_source=, explicit_confirm=)` 实时决策；`same_source` 经 `registry.heterogeneous` 计算 | 严格遵守零 DDL；关键卡点识别判据（a/b/c）由 M10 在触发阶段确定后传入 |

> 以上偏差均不触及 `db.py` / `routes/` / `app.py` 既有逻辑与 M0 锁定的 16 库对象（零 DDL）。
