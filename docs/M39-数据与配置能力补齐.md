## 二、关键取舍

### A4 删除特意不解密

`FileBackend.delete` 只做 `unlink`，**不走解密**。原因：如果删除也需要口令，
那么密钥库一旦锁定（没设 `HPSL_MASTER_PASSPHRASE`），用户就永远删不掉一把填错的密钥。
删除是不需要知道明文的操作，多要一次解密只会制造死锁。浏览器实测：
存密钥 → 去掉口令重启 → 页面顶部提示「密钥库当前不可用」→ 仍能点「清除密钥」成功。

同时**遍历 keyring 与文件保险库两个后端**，避免「钥匙串删了、文件里还留一份」的半删除态。

### A1 显式指定模型时不允许静默降级

`pick_default_model` 的自动逻辑是「第一个有密钥的厂商的第一个模型」。若把它直接当作
「用户指定」的执行路径，会出现：用户选了 `qwen-plus` 但千问没配密钥 → 系统悄悄改用
deepseek → **用户以为在用千问，账却记在 DeepSeek 上**。所以 `resolve_role_model`
在指定模型无密钥时直接抛 `A040003`，文案给出两条出路（去「密钥」页填 / 改回自动选择）。

设置页的「实际会用什么」列会**提前**把这个问题显示出来，不必等到调用失败：

```
挑错者 | [qwen-plus ▾] | 角色「挑错者」指定用 qwen-plus，但厂商「千问 Qwen（MaaS）」
                        没有可用密钥；请到「密钥」页填写，或到「设置」把该角色改回自动选择
```

存储上是 `project.config.role_models`（JSON 键），**零 DDL**；`KNOWN_FIELDS` 已登记，
JSON 往返后可读回。写入语义是「整体替换」：前端每次提交六角色的完整快照，
空值被剔除，因此「把某角色改回自动」＝提交时不带该键。

### B1 预检放在创建 session 之前

`_ensure_keys` 的位置在 `_ensure_registered` 之后、`db.write("session", …)` 之前。
此前不做预检的后果是：三家配了两家密钥 → 会话已建、前两家已计费、第三家才失败，
用户花了钱拿不到完整答案。现在失败时**零会话、零费用**，错误文案里直接写明这点。

自动模式还改为**只挑已配密钥的厂商**；不足 2 家时区分两种提示（0 家 / 只有 1 家并报出是哪家），
不再让人去翻 `models.yaml`。

### B2 恢复改为局部刷新

原来 `HX-Refresh: true` 会让整页刷新，「已从快照恢复：xxx（留底 yyy）」这句提示瞬间消失，
和 M35 建单元改掉的是同一类问题。现在返回结果片段 + `#backup-list` / `#backup-count`
的 OOB 同步，用户能看见自己刚做了什么。浏览器实测用 `window` 标记确认页面未被重载。

## 三、一处需要更正的判断

本轮盘点初稿把「快照无限堆积」列为待修问题。**这个判断是错的**：
`db.backup_project` 内部一直会调 `rotate_backups`（日 7 + 月 12 的祖父-父亲-儿子式保留），
`pre-restore-*.db` 也有 `cleanup_pre_restore`（保留最近 3 份）。
容量控制本来就有。

所以 A3 的真实定位是「**想立刻删掉某一份**」这个手动场景（误导出的快照、想马上腾空间），
不是补容量控制。文档与提交信息都按这个口径写，避免夸大。
