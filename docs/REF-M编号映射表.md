## 0. 用法（先读这一节）

三套编号体系并存，**编号相同、语义不同**。今后引用时一律带前缀，不再裸写「M2」：

| 写法 | 含义 | 出处 |
|---|---|---|
| `A-Mx` | **版本路线里程碑**（方案 §10，M0–M5 属 v0，M6–M7 属 v1） | `paper/项目制学习框架工具：综合方案.md` §10 |
| `B-Mx` | **能力模块编号**（系统设计 §3.2.M1–M10，是"模块"不是"排期"） | `.workbuddy/delivery/系统设计.md` §3.2 |
| `C-Mx` | **实现里程碑**（`docs/Mx-*.md`，M0–M23，按实际交付顺序） | `docs/` 下各里程碑文档 |

一句话记忆：**A 是"先做什么"（路线），B 是"分几块"（模块），C 是"实际怎么排的"（交付）**。C 前半段（M0–M10）沿用 B 的切分，后半段（M10B/M11–M23）是 B 之外的新增。

## 1. 三套体系总览

| 项 | A 方案 §10 | B 系统设计 §3.2 | C 实现里程碑 |
|---|---|---|---|
| 编号范围 | M0–M7 | M1–M10 | M0–M23（含 M10B 六批） |
| 编号语义 | 版本路线（v0=M0–M5，v1=M6–M7） | 能力模块（BD/BC 归属） | 交付批次（含 UI/迭代） |
| 是否有 M0 | 有（骨架） | 无（从 M1 起） | 有（数据底座） |
| 一份 M 是否单一功能 | 是（较粗） | 是（一模块） | 否（M4/M11 等含多能力） |
| 状态 | v0 已实现，v1 多数未实现 | 与 C-M1–M10 基本一一对应 | 全部已交付（`336 passed`） |
| 权威性 | 产品意图 | **锁定基线（只读，改动走 CHG）** | 实际事实（代码即真相） |

**为什么会有三套**：方案 §10 是"给 AI 的任务拆分"，按 v0/v1 版本排；架构交付把 v0 拆成 10 个能力模块（B-M1–M10，与 §3.2 的 BD/BC 对齐）；实现期直接沿用 B 的模块切分做 C-M0–M10，然后按用户需求继续加 M10B/M11–M23。三方各自自洽，但**从未写过映射表**——本文档补这一课。

## 5. 六个最容易误读的错位（重点）

1. **`A-M1`（模型适配）≠ `C-M1`（Web 接入）**——两套编号在 M1 上完全撞车，最常被误引。
2. **`A-M2`（账本+状态机）在实现里被拆开**：状态机在 `C-M2`，账本表在 `C-M0`，编排在 `C-M7`。
3. **`A-M5`（挑错+打包）只兑现了一半**：挑错 → `C-M5`；打包（备份/导出/README/撤销）散到 `C-M1/M10B4/M11`，Docker 未做。
4. **`A-M6/M7`（v1）大部分没做**，但其中的"复测""四平面""Gemini"被提前：复测 → `C-M2/M6`，四平面 → `C-M9`，Gemini → `C-M22`（占位）。
5. **`B-M5`（判分与闭环）在 C 中被切成两个里程碑**：判分/闭环 → `C-M4`，挑错 → `C-M5`。看到 "M5 挑错"时不要以为它对应 `B-M5` 的全部。
6. **`B-M10`（Web 接入）不是一个里程碑**，在 C 中展开为 `C-M10` + `M10B1–6` + `C-M11` 及后续所有 UI 里程碑。

## 6. 今后的引用规范（建议写入 `docs/` 约定）

- 引用路线意图：`A-Mx`（例：`A-M5` 决定把"关键卡点必挑错"放进 v0）。
- 引用架构契约：`B-Mx`，并同时给章节号（例：`B-M6` / 系统设计 §3.2.M6）。
- 引用实现事实：`C-Mx` + 具体文件（例：`C-M5` 的 `hpsl/engine/claim_check.py`）。
- 禁止裸写「M2」——在跨文档语境中它至少有三义。
- 新里程碑继续用 `C-` 体系（M24…），不要回填到 A/B。
