## 5. 缺陷清单与定级

### D-M2-1（严重 → 已闭环）

| 项 | 内容 |
|---|---|
| 标题 | 复测后 review 行被置失活，导致 2/7/21 循环断裂 |
| 根因 | `submit_review` 曾将 `review.result` 写为"通过/未通过"，使 `due_reviews` 的 `result IS NULL` 过滤永久失活该活跃行 |
| 修复 | 保持 review 活跃（`result` 维持 NULL）+ 仅推进 `due`；复测结果以 `attempt(kind='复测')` 为准 |
| 独立验证 | 杜见微 C7 + `test_review_interval_cycling`：独立复现 2→7→21→21 全程，每次 `review.result` 恒 NULL、活跃行恒 1 |
| 结论 | **闭环确认**，不再复现 |

### O-M2-1（一般 → 已闭环，采用主理人裁决方案 a）

| 项 | 内容 |
|---|---|
| 标题 | `LEARN→VERIFY` 直接跳过 PRODUCE 路径原不被支持 |
| 现象 | 原 `TRANSITIONS[LEARN]=(PRODUCE, PICK)` 未含 VERIFY，合法性校验先于闸门 → `LEARN→VERIFY` 直接抛 A020001，与任务书 B 项（无 reason→A020003、带 reason→skipped_produce=1）不符 |
| 主理人裁决 | 采用方案 (a)：增补 `VERIFY` 到 `TRANSITIONS[LEARN]`（闸门代码已能正确处理该边） |
| 落地 | 高建瓴改 `state.py` 为 `LEARN: (PRODUCE, VERIFY, PICK)`，新增 2 例（`test_learn_to_verify_no_reason_rejected` / `test_learn_to_verify_with_reason_skips`），pytest 63→65 passed |
| 结论 | **闭环确认**。M2 质量结论由「有条件通过」升级为「无条件通过」 |

### O-M2-2（轻微 / 文档一致性 → 已闭环，CHG-02）

锁定基线 `系统设计.md` §3.2.M6.5 原写"review.result=通过/未通过"，与需求基线 D-M2-1 修复（result 维持 NULL）冲突。M2 收口后，主理人北城明确指令**直接修订锁定基线原文**（覆盖常规「一字不动」流程）：将 `系统设计.md`（系统图 D3 / §3.2.M6.4 序列图 / §3.2.M6.5 流程逻辑与写回纪律）、`UserStory.md` §5.4.4、源 `pic/uml/bf-02.mmd` 的复测写回描述统一对齐为「review 保持活跃（result 维持 NULL）仅推进 due，复测结果以 attempt 为准」；重算 `系统设计.md`/`UserStory.md` 指纹并登记 `CHG-02`，`verify_baseline.py` 复跑 8/8 OK（BASELINE INTACT）。纯文档级，引擎实现未变。

### O-M2-3（轻微 / 健壮性强健性，不阻塞）

复测首档间隔由 `(due - last_verified_at)` 推导而非显式阶段计数；全新概念路径（2→7→21→21）已验证正确，但 `last_verified_at` 与入队时间相差较远的概念首档可能直接跳到 21。建议后续明确推导语义或改显式阶段计数，AC 用例未覆盖此边。
