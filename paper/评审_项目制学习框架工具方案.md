# 《项目制学习框架工具：综合方案》评审

评审对象：资料库文档「项目制学习框架工具：综合方案」（11 节 + 代码骨架 + 数据模型）
评审基准：论文《高阶牵引式学习法与工具无关型框架》（以下简称「论文」）原文
评审日期：2026-10-15

---

## 总体判断

这份方案是我见过同类设计文档里质量相当高的一份：边界感诚实（"这些只能降低风险，不能保证""不承诺学习效果"）、测试设计具体（每条测试都对应一条失效模式）、AI 辅助开发的约定务实（先写验收测试、一次只改一个模块、关键模块人工审）。**它已经具备开工条件。**

但有一条主线问题贯穿全文：**工程化的过程中，论文最核心的三条机制被不同程度地削弱或丢失了**——「回归主线」「关键卡点必挑错」「重述判据固定三问」。这三条恰恰是论文区别于"普通 AI 学习法"的地方。工具做出来后如果这三条不在，它会是一个"带账本的聊天界面"，而不是 TLF 的实现。

按严重程度分四级：**A 类 5 条**（动手前必须改）、**B 类 8 条**（M2 前必须定）、**C 类 8 条**（实现时会出 bug）、**D 类 8 条**（其他）。

## A 类：会让核心机制走样（动手前必须改）

| # | 问题 | 依据 | 后果 |
| --- | --- | --- | --- |
| A1 | **丢失「回归主线」阶段** | 论文 3.2 节六阶段：选单元 → 记缺口 → 补缺口 → **回归主线（完成单元产出）** → 强制验证 → 整合。论文还专门写了一段说明强调"强制验证位于回归主线之后"，并声明"全文统一采用此顺序" | 文档七步为：创建项目 / 初始化提问 / 选题 / 学习 / 验证 / 判定 / 整合。**"学习"一步只有"答案机按需回答"，没有"完成单元产出"**。状态机 `LEARN → VERIFY` 直接转移，也没有对应状态 |
| A2 | **关键卡点的挑错从「闭环必要条件」降级为「可选触发条件」** | 论文 4.3 节明确："唯一例外是当该单元涉及关键卡点时，**异模型挑错通过才成为闭环条件**" | 文档把挑错列为"触发条件"之一（关键卡点 / 代码数字引用 / 答案机分歧 / 手动点击），但闭环判据只写"重述与边界题得分都达 0.7"。**触发 ≠ 必要**：挑错发现错误残留后仍可闭环，防御共识幻觉的最后一道闸门被拆了 |
| A3 | **重述判据改为每次由出题者生成，失去跨单元可比性** | 论文 4.3 节：脱稿重述的通过条件是**固定的三个必答问题**（目的 / 机制 / 边界，4.2.1 节），"三问完整答出，且使用自己的组织方式" | 文档让出题者"生成重述与边界题的评分要点"。判据每次都变 → **"通过率 60%–80%"这个指标失去意义**（不同单元的 0.7 分不是同一把尺子），后续引入 Elo 也无从校准 |
| A4 | **架构五层与论文三层不一致，且"角色层"被占用** | 论文 7.3 节：TLF = **角色层（L1）—流程层（L2）—治理层（L3）** | 文档架构图为 项目层 / 编排层 / 角色层 / 模型适配层 / 治理层。同名不同义：论文的"角色层"是契约定义层（含四个过程角色），文档的"角色层"只放模型实例。**自己论文里的术语在自己工具里漂移**，开源后最难解释 |
| A5 | **「强制异构」与「降级并警告」自相矛盾** | 风险表对策写"强制异构并警告；分歧优先于投票" | 正文多处写"只有一个厂商的 key 时仍可运行，降级为同源提示并警告"。v0 明确允许单一厂商运行 + 挑错者与答案机同源。**而 v0 恰恰是唯一会被实际使用的版本** |

### A1 展开（最严重）

论文把"补完缺口即结束，未完成任务"列为六阶段表的**常见偏差**（表 3-1 第 4 行），并为"验证位于产出之后"写了专门的理由：

> 知识在未被使用时，学习者的理解往往只是"解释层面的理解"；而在完成任务后验证，检验的是"应用层面的理解"，后者才是 HPSL 的目标。

文档的状态机把这一步整个跳过了——**论文明令防止的那个偏差，被工具的状态机制度化了**。学习者补完缺口点"验证"，系统照单全收，从不要求他先拿出单元产出。

建议：在 `LEARN` 与 `VERIFY` 之间加一个显式的产出步骤（可叫 `PRODUCE`），要求学习者提交单元产出（一段代码、一份分析、一个结论），并把它记入 `unit`。如果担心摩擦，可设为可跳过，但**必须像强行闭环一样打标记、不计入完整进度**，并在风险平面显示。

### A3 展开

论文的重述判据是**稳定的三问**（目的 / 机制 / 边界），好处是：学习者知道会被问什么、跨单元可比、不需要 AI 参与判定。文档改为 AI 生成评分要点，引入三个新问题：判据漂移、评分要点本身可能有错（风险表已承认）、暴露给"模型输出"这一不可靠环节。

建议：**重述沿用论文固定三问**（可做成界面上的三个输入框 + 三条自查勾选项），出题者只生成**边界题**及其评分要点。重述这层保持确定性，边界题那层才交给模型。这样 A3 与"评分要点有误"风险同时收敛。

## B 类：AI 拿这份规格做不出来 / 数据模型缺口（M2 前必须定）

文档第十节声明"本文档就是给 AI 的规格说明：每个里程碑的'内容'和'验收'可以直接作为任务描述"。按这个标准，以下条目 AI 无从下手：

| # | 缺口 | 说明 |
| --- | --- | --- |
| B1 | **缺口分级判据未写入规格** | 全文只说"书记员给出分级建议""用户批量确认"，从未定义一/二/三级怎么分。论文 3.4 / 表 3-4 有：一级＝阻塞当前任务（速度优先，单 AI 快查）；二级＝不阻塞、可批量；三级＝仅记录作后续牵引点。**这句不抄进来，AI 实现的分级就是随机的** |
| B2 | **关键卡点三项判据未写入规格** | 论文 3.6 节给了明确的三条：(a) 本单元多环节反复使用；(b) 误解会导致后续多个结论系统性错误；(c) 决定后续学习方向分叉。文档只出现"关键卡点"四个字，判据缺失 → 挑错者的触发规则无法实现 |
| B3 | `llm_call`** 无 **`session_id`** / **`unit_id` | 第五节承诺"**每次会话显示花费估算**，设预算上限"，但 llm\_call 只有 role/provider/model/tokens/cost。**无法按会话聚合，功能实现不了** |
| B4 | `concept`** 表无 **`verify_status`** / **`last_verified_at` | 第五节护栏写"概念的验证状态随时间衰减，由复测刷新"，M6 也写了"验证状态衰减"。但 concept 表只有 `(id, name)`，`verify_status` 只存在于 card 表。**衰减无处存储** |
| B5 | `gap_candidate`** 无 **`level` | 流程要求书记员"给出分级建议"，但候选表只有 `(id, unit_id, text, source_turn, status)`。建议的分级存哪？ |
| B6 | `claim_check`** 无 **`unit_id`** / **`session_id` | 质量平面度量"挑错残留数"，风险平面要按单元归因。当前表无法归属到任何单元或会话 |
| B7 | `turn`** 无 **`provider`** / **`model` | "挑错者可并行调用多个异构模型，各自的清单并排展示"——按什么分组展示？没有模型字段 |
| B8 | `unit`** 无 **`difficulty_band` | `topic_picker` 契约的 allow 里含 `difficulty_band` 作为**输入**，但生成后的单元难度档位没有落表字段，M6"建议难度区间"无法回溯验证 |

### 附加：状态机两个结构问题

- **B9｜REVIEW 归属混乱。** 延迟复测是**跨单元**的（2/7/21 天后复考旧概念），但状态机是**单元内**的。`REVIEW → LEARN` 会把旧概念的复测结果写进当前单元的账本。且 `REVIEW` 只能从 `PICK` 进入——**用户不开始新单元，到期复测永远不触发**，与第五节"首页主按钮：继续当前单元，或做到期复测"直接矛盾。建议 REVIEW 做成独立于单元状态机的到期队列，首页直接消费。
- **B10｜降级动作无处记录。** `LEARN: {"VERIFY", "PICK"}`，注释说"PICK：熔断后降级重选"。但降级 ≠ 重新选题；且 `unit` 只有 `chosen_from` 没有 `degraded_from`，`LEARN → PICK → LEARN` 的循环不留下任何痕迹，"熔断次数"这项风险度量就无从统计。

## C 类：代码骨架里会出 bug 的地方

| # | 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| C1 | `safe_path()` | **真实路径穿越漏洞。** `p = (base / rel).resolve()`——pathlib 的 `/` 运算符遇到**绝对路径会丢弃 base**：`base / "/etc/passwd"` 直接得到 `/etc/passwd`，紧接着 `base not in p.parents` 成立 → 抛异常前路径已解析成功；若 rel 形如 `/tmp/evil` 且 base 恰好在其 parents 中则直接放行。**必须先拒绝绝对路径的 rel** | 开头加 `if Path(rel).is_absolute(): raise` |
| C2 | `Provider.chat` 协议 | **无 **`response_format`** / JSON mode / tool calling。** 但系统重度依赖结构化输出：评分要点、缺口分级、挑错清单、概念图关系。各家能力差异极大（OpenAI 有 json\_object、Anthropic 无原生 JSON mode）。**协议层不表达这个，AI 实现出来一定是裸解析字符串** | 协议增加 `response_format` 参数，每个 Provider 声明自身能力 |
| C3 | `Reply` dataclass | 无 `finish_reason`。`max_tokens: int = 1500` 对"边界题 + 评分要点"很可能不够，**截断后 JSON 解析失败且无法区分是截断还是正常结束** | 加 `finish_reason`，截断时报错或重试 |
| C4 | `pass_rate()` | **混入强行闭环单元。** 只过滤 `confirmed_score is not None`，不排除 `forced_close=1` 的单元。而强行闭环恰恰是"未达标"，会通过拉低/拉高通过率**污染难度建议**（`suggest_band` 用它决定升降） | 计算口径显式排除强行闭环，与"不计入进度"保持一致 |
| C5 | `zero_gap_ratio()` | **可被不作为操纵。** 用 `not s.gaps` 判断，但书记员的候选缺口要用户确认后才入 gap。**用户从不确认 → 零缺口占比虚高 → 误触发升难度** | 分母改为"已确认的会话"，或把未确认候选计入分子 |
| C6 | `suggest_band()` | **实际优先级与声明不符。** 第四节声明"平面冲突时优先级是风险、质量、节奏、进度"，但函数按 节奏(l1) → 节奏(zero\_gap) → 质量(pass\_rate) 顺序返回，**节奏压过质量，且完全没有风险平面的输入** | 显式实现四级优先级；风险平面信号（分歧、无不确定标注）应最先判定 |
| C7 | `assemble()` | `for k in allow`（`allow` 是 **set**）→ 迭代顺序随进程启动的 hash 随机化而变 → **同一输入生成的 prompt 顺序不同** → `input_hash` 不稳定、`test_contracts` 不可复现 | `allow` 改成有序结构（tuple / list） |
| C8 | `heterogeneous()` | `family` 单值**无法表达蒸馏关系**。第七节明确"同厂商或蒸馏关系不算异构"，但 DeepSeek 系与 Llama 系是蒸馏关系，`family` 只能取一个值，配置模型与设计约束不匹配 | `family` 改为列表（可属多谱系），或增加 `derived_from` 字段 |

## D 类：其他

| # | 问题 |
| --- | --- |
| D1 | **Docker 部署与"只监听 127.0.0.1"直接冲突。** 容器内 127.0.0.1 宿主机访问不到，需改 bind 到 0.0.0.0 —— 而这正是安全方案要防的。文档未说明 Docker 场景下如何取舍 |
| D2 | **keyring 降级方案的口令来源与 KDF 未定义。** "不可用时用口令加密的本地文件"——口令从哪来？存本地就是循环；每次启动输入则"一键部署"体验受损。也没提 KDF（PBKDF2/Argon2 + salt） |
| D3 | **「4–5 倍成本」的论证不成立。** 第七节用"论文估算交叉验证成本约 4–5 倍，因此默认使用最低验证配置"。但 4–5 倍是**多答案机并行**的成本，v0 本来就只有一个答案机。v0 关掉追问/挑错的真实原因是摩擦，不是这个倍数 |
| D4 | **挑错者输入口径不一致。** 第二节表格写"学习者的**解释**和原问题"，原则三写"挑错者只看**待检断言**"，契约里字段叫 `claim`。三者不是一回事，实现时会分歧 |
| D5 | **使用日志表述矛盾。** 第六节"使用日志默认关闭，仅存本地"，第十一节"默认关闭的本地日志用于校准参数"。读起来像是两套东西，建议改成"默认关闭；开启后仅存本地，用于参数校准" |
| D6 | **SQLite 并发写未设计。** 第五节要求评分要点生成与核对、挑错者多模型评审"后台并行"，但只说了 WAL 模式，没提写锁、超时、连接池。并发写 `attempt` / `claim_check` 会撞 SQLITE\_BUSY |
| D7 | **效果验证方法论过弱。** "用自己的延迟复测通过率做自我对照，样本小，仅作参考"——n=1 且无随机化。建议在文档里直接定性为**个案观察（n=1，非对照实验）**，避免开源后被误引为效果证据 |
| D8 | **测试缺三块：** 无 `test_pacing`（`suggest_band` 是核心逻辑却无测试）、无 `test_cost`（预算熔断）、无 `test_retrieval`（v1 检索）。`test_contracts` 只断言提问者，出题者的边界题质量无自动断言 |

## 建议砍掉的东西

按"每多一块没经过实际使用的功能，就多一块要维护的代码"这条你自己写的原则，以下三块建议直接删：

| 项 | 理由 |
| --- | --- |
| **Elo 评分模型（v2）** | 单人自用工具，样本量几乎永远达不到建模要求。规则层（通过率、零缺口占比、自评差距）已经够用，Elo 是为一个不会到来的数据量预留的复杂度 |
| **桌面安装包（v2）** | 目标用户明确是"会用 API key 的技术型学习者"，`pipx + hpsl serve` 完全够。安装包是分发成本最高的一种形态，排在 v2 末尾不划算 |
| **手动粘贴模式（v2）** | 你自己写了"此时无法自动验证角色输入的隔离，只能靠界面分页展示"——**隔离是这个工具的核心，一个无法验证隔离的模式等于把核心卖点关掉**。不如把精力放在让 API 接入更省事 |

反过来，**建议从 v2 提前到 v0 的一件事**：把\*\*苏格拉底追问（提问者）\*\*纳入默认验证配置。它不需要异构模型、成本不高，而论文 4.2.2 节把它作为对抗"元认知惰性"的主要手段。当前 v0 默认只有重述 + 边界题，等于论文四个验证操作里只实现了两个——工具的"验证"卖点在 v0 是打折的。

## 一句话总结

**这份方案可以开工，但请先把 A 类的 5 条改掉**——它们不是细节问题，是"做出来的工具还兑现不兑现论文承诺"的问题。最要紧的一条是 A1：**论文花了专门篇幅强调"验证必须在完成单元产出之后"，而这份状态机把这一步跳过了**，于是论文点名的那个偏差（补完缺口就结束）变成了工具的默认行为。

`REVIEW` 我按 B9 做成了完全独立的跨单元到期队列（`REVIEW_INTERVALS = (2, 7, 21)`，结果只写回 `concept`）。代价是**复测与单元流程彻底解耦**，好处是旧概念成绩不再污染当前单元账本、且不开新单元也能复测。如果你希望复测结果反过来推动当前单元降级，需要再补一条从队列到节奏平面的回路。
